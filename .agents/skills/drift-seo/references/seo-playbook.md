# DriftLock SEO/GEO Playbook

Use this reference when producing search-ready DriftLock content. It combines
repo-local product language with people-first SEO, keyword intent, E-E-A-T, and
topical authority practices.

## Source Notes

Consult only these sources when the user asks for external grounding or current
SEO best practices:

- Google helpful content:
  https://developers.google.com/search/docs/fundamentals/creating-helpful-content?hl=en
- Ahrefs SEO content strategy:
  https://ahrefs.com/blog/seo-content-strategy/
- Ahrefs keyword intent:
  https://ahrefs.com/blog/keyword-intent/
- Search Engine Land E-E-A-T guide:
  https://searchengineland.com/guide/google-e-e-a-t-for-seo
- Search Engine Land topical authority guide:
  https://searchengineland.com/guide/topical-authority

Core takeaways to apply:

- Create people-first content for a real DriftLock audience, not pages made
  primarily to capture search traffic.
- Make the "Who, How, and Why" clear when it affects trust: who created or
  reviewed the content, how the product knowledge was gathered, and why the
  page exists for the reader.
- Use keyword intent as a filter before drafting. Separate informational,
  commercial, transactional, navigational, branded, and mixed intent.
- Prioritize content ideas by traffic potential, business potential, and ranking
  potential, then keep quality high with the R-E-A-C-H lens.
- Treat E-E-A-T as a credibility framework, not a magic ranking switch. Trust is
  the center: support claims with product evidence, sources, and clear limits.
- Build topical authority with focused pillar pages, supporting clusters,
  consistent terminology, and internal links across related DriftLock concepts.
- Refresh content when intent, product behavior, SERPs, or competitor coverage
  change. Do not update dates without substantive changes.

## Decision Framework

Before producing content, decide:

```txt
1. Audience: buyer, developer, founder, reviewer, or AI-assisted team lead.
2. Intent: informational, commercial, transactional, navigational, branded, or mixed.
3. Business potential: how directly the topic can show DriftLock's value.
4. Topical role: pillar, cluster, comparison, FAQ, docs landing, or launch post.
5. Evidence angle: product mechanism, CLI command, contract example, CI report,
   diagnostic, benchmark, source, or explicit limitation.
6. Internal links: install, docs, proof, contracts, CLI, ESLint, or dogfood pages.
```

Default ranking for DriftLock content ideas:

```txt
High: intent preservation, @drift contracts, AI-assisted TypeScript, PR proof,
vibe-coding governance, source-of-truth drift, AI coding CI checks.
Medium: general AI coding best practices, code review workflows, TypeScript
quality, developer tooling comparisons.
Low: broad AI productivity, generic SEO, unrelated startup or automation topics.
```

## Intent Patterns

Informational:

```txt
Use for definitions, guides, and educational posts.
Answer the question first, then show a DriftLock mechanism or example.
Example: "What is code intent drift?"
```

Commercial investigation:

```txt
Use for comparisons, proof pages, governance pages, and buyer education.
Show what DriftLock does, what it does not do, and when it is the right fit.
Example: "DriftLock vs AI code review"
```

Transactional:

```txt
Use for install, onboarding, CLI, or CI setup pages.
Lead with concrete commands and prerequisites.
Example: "Install DriftLock in a TypeScript repo"
```

Branded or navigational:

```txt
Use for product, docs, release, and proof pages.
Keep canonical names exact: DriftLock, @drift, drift-lock, @drift-lock/cli.
```

Mixed intent:

```txt
Choose one primary page intent or split the topic into separate pages.
Do not force one article to sell, teach, compare, and onboard at the same time.
```

## Content Patterns

Homepage or product page:

```txt
H1: Lock the intent. Ship the vibe.
Lead: DriftLock turns local engineering intent into agent context, ESLint
feedback, and CI checks so AI-assisted TypeScript changes cannot silently drift
from critical sources of truth.
Sections: problem, mechanism, proof workflow, example contract, supported
checks, install, FAQ.
Evidence: real package names, CLI commands, @drift syntax, supported limits.
```

Feature page:

```txt
H1: Pull Request Proof for AI-assisted code changes
Lead: Show reviewers whether protected intent was preserved, explicitly changed,
or left unresolved before merge.
Sections: reader pain, how it works, report fields, CI usage, limits, FAQ.
Evidence: proof command, report fields, diagnostic examples.
```

Blog or educational article:

```txt
Title shape: "How [audience] can [solve pain] without [bad tradeoff]"
Intro: define the pain in one paragraph, then state the practical answer.
Body: explain the failure mode, show a concrete DriftLock example, compare with
tests/review, and end with a realistic adoption path.
Evidence: code sample, CLI command, product limitation, or repo-backed example.
```

Comparison page:

```txt
Open with the honest boundary: DriftLock complements the compared category.
Compare by job-to-be-done, not by feature checklist only.
Repeat that DriftLock protects declared local intent; it does not replace tests,
review, security scanning, or runtime validation.
```

## Topical Authority Map

Use these clusters to keep DriftLock coverage focused:

```txt
Pillar: AI intent preservation
Clusters: code intent drift, @drift contracts, SSOT checks, agent context,
AI-assisted TypeScript, vibe-coding governance.

Pillar: Pull Request Proof
Clusters: proof report, intent preservation rate, accepted contract changes,
unresolved drift, CI checks, reviewer workflow.

Pillar: DriftLock for developer workflows
Clusters: CLI install, ESLint feedback, contract syntax, context command,
diff summary, explain diagnostics.
```

Internal-link rules:

```txt
- Link pillar pages to every relevant supporting cluster.
- Link cluster pages back to their pillar and to adjacent clusters.
- Use descriptive anchor text that names the concept, not "click here".
- Prefer links that help the reader complete the job behind the query.
```

## SEO/GEO Checklist

Before finalizing content, check:

```txt
- One clear intent is selected before drafting.
- The page helps DriftLock's actual audience if they arrive directly.
- The H1 names the product, offer, or exact problem without exaggeration.
- The intro answers the query within the first 100 words.
- The page demonstrates first-hand product knowledge or clearly sourced analysis.
- Claims are concrete, limited, and grounded in repo behavior.
- The content adds original value instead of summarizing generic AI tooling advice.
- E-E-A-T cues are present where expected: author, source, method, proof, limits.
- Topical role is clear: pillar, cluster, comparison, FAQ, docs, or launch.
- Internal links connect the page to related DriftLock topics.
- Metadata includes the product entity and main query intent.
- Structured data is suggested only when it matches visible content.
- Content includes SEO and AI-era terms without stuffing.
- Refresh guidance is included when product behavior or search intent may change.
```


## JSON-LD Guidance

Suggest schema only when it matches the page:

```txt
SoftwareApplication: product or homepage.
Article: educational article or launch post.
FAQPage: visible FAQ section with matching questions and answers.
Organization: brand/about/footer-level entity data.
BreadcrumbList: docs, blog, or nested content.
```

Keep schema consistent with visible page content. Do not invent ratings,
reviews, prices, organizations, or availability.

## Claim Boundaries

Allowed:

```txt
DriftLock makes declared local intent explicit and checkable.
DriftLock helps reviewers see whether protected intent changed.
DriftLock complements tests and code review.
DriftLock can fail CI when supported invariants drift.
```

Avoid:

```txt
DriftLock guarantees AI-generated code is correct.
DriftLock prevents all regressions.
DriftLock replaces human review.
DriftLock secures your application.
DriftLock guarantees LLM citations or Google rankings.
```
